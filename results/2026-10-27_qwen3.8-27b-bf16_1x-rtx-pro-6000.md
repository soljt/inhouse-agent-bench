# Qwen3.8-27B BF16 on 1x RTX PRO 6000: vLLM startup report

2026-10-27 · RunPod Secure Cloud (EU) · first successful serve, for a quality comparison against the FP8 runs

Numbers below are what vLLM reported in its log, not benchmarks. The log covers startup and the first 9 minutes
of the suite (one agent at a time).

## Setup

| Item | Value |
| --- | --- |
| GPU | 1x NVIDIA RTX PRO 6000 Blackwell Server Edition, 97,887 MiB |
| Template | RunPod PyTorch, plus `cuda-toolkit-13-0` (`CUDA_HOME=/usr/local/cuda-13.0`) |
| vLLM | 0.30.0 |
| Weights | `Qwen/Qwen3.8-27B`, 55.6 GB BF16, from the container disk |

```bash
vllm serve /root/models/qwen3.8-27b-bf16 \
  --served-model-name qwen3.8-27b \
  --host 127.0.0.1 --port 8000 \
  --tensor-parallel-size 1 \
  --max-model-len 131072 \
  --max-num-seqs 256 \
  --gpu-memory-utilization 0.92 \
  --kv-cache-dtype fp8 \
  --reasoning-parser qwen3 \
  --enable-auto-tool-choice --tool-call-parser qwen3_xml \
  --api-key "$VLLM_KEY"
```

The same command as the FP8 serve (`2026-10-07_qwen3.8-27b-fp8_1x-rtx-pro-6000.md`) with BF16 weights and
`--max-num-seqs 256`. Without it, startup failed with `max_num_seqs (1024) exceeds available Mamba cache blocks
(661)`: each sequence slot needs a block for its linear attention state, and with BF16 weights vLLM's default of
1024 slots doesn't fit.

| Attention backend | FlashInfer (decode backend `xqa`, KV cache `float8_e4m3fn`, sm120) |

| Model load total | 6.0 s, 51.1 GiB GPU memory |
| torch.compile | 19.1 s |
| CUDA graph capture | 35 s, 1.31 GiB |
| Engine init (profile, KV cache, warmup) | 94.1 s |
| Start to `Application startup complete` | about 2 min (14:55:42 to 14:57:37) |
| Available KV cache memory | 32.11 GiB |
| GPU KV cache size | 975,758 tokens |
| Max concurrency at 131,072 tokens/request | 7.44x |

Derived: about 34.5 KiB per token (32.11 GiB / 975,758 tokens), the same as the FP8 serve, since the KV cache
type is the same. The BF16 weights take 22.6 GiB more than FP8 (51.1 against 28.5), which costs 22 GiB of KV
cache (32.1 against 54.2), and the concurrency drops from 12.58x to 7.44x.

## During the suite

From `bench/vllm_stats.py` over 15:10 to 15:19 (pod clock):

| Running requests | Samples (10 s) | Generation tok/s, mean / max | Prompt tok/s, mean | KV cache %, mean / max |
| --- | --- | --- | --- | --- |
| 1 | 47 | 24.0 / 48.8 | 116 | 4.0 / 5.8 |
| 2 | 2 | 42.2 / 44.1 | 682 | 2.5 / 2.5 |

- No requests waited for KV cache or a slot.
- Prefix cache hit rate at the end: 84.4%.
- About 24 generated tokens per second with one agent, against about 75 for Qwen3.8-Flash-Next NVFP4 on the same
  card (`2026-10-27_qwen3.8-flash-next-nvfp4_1x-rtx-pro-6000.md`). The dense model reads all its BF16 weights for
  every token. Runs took 6 to 10 minutes longer than the same tasks on FP8.
