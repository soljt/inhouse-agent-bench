# GLM-5.3-Flash FP8 on 4x RTX PRO 6000: vLLM server report

2026-10-14 · RunPod Secure Cloud (EU) · first serve, load test and suite

Startup numbers are what vLLM reported in its log (saved as `bench/results/vllm-glm-5.3-flash-261014.log`,
second start only); load numbers are `bench/vllm_stats.py` over that log.

```bash
export VLLM_ENGINE_READY_TIMEOUT_S=3600
vllm serve /root/models/glm-5.3-flash-fp8 \
  --served-model-name glm-5.3-flash \
  --host 127.0.0.1 --port 8000 \
  --tensor-parallel-size 4 \
  --max-model-len 131072 \
  --max-num-seqs 16 \
  --kv-cache-memory=8000000000 \
  --no-enable-flashinfer-autotune \
  --reasoning-parser glm47 \
  --enable-auto-tool-choice --tool-call-parser glm47 \
  --api-key "$VLLM_KEY"
```

The first start used `--gpu-memory-utilization 0.95` instead of `--kv-cache-memory`. A start before that, with
`--kv-cache-dtype fp8` and vLLM 0.30.0, failed with `pe_dim must be 64 for fp8_ds_mla`, so the KV cache is BF16.

Derived:

- **About 35 KB of KV cache per token across the four GPUs** (8.8 KB on each): 4 x 7.45 GiB / 909,560
  tokens, the same at both starts. Our research estimate was 40 KB at FP8, 46 KB at BF16.
- **Memory per GPU:** 94.97 GiB seen, of which 78.3 GiB weights and memory outside PyTorch, 6.3 GiB
  activations, 0.2 GiB CUDA graphs, 7.45 GiB KV cache: about 2.7 GiB left. vLLM said 9.1 GiB of KV cache would
  fill the GPU completely.
- **Against the target load of 4 agents x 131k tokens** (524,288 tokens), the KV cache holds 1.7x that.

Warnings in the log, none of them errors:

- `Custom allreduce is disabled because it's not supported on more than two PCIe-only GPUs`: at 4 GPUs vLLM
  uses NCCL alone, so `--disable-custom-all-reduce` would change nothing here.
- `Sparse MLA layer has no dense-MHA prefill path; using the top-k MQA path only.`
- `Default vLLM sampling parameters have been overridden by the model's generation_config.json:
  {'temperature': 1.0, 'top_p': 0.95}`: the model's recommended sampling, kept.
- Triton kernels compiled during the first requests (`_kpool_tail_seed_kernel` and others): a one-off latency
  spike, not a steady cost.

## Suite

`bench/suite.py --timeout-min 30`, 28 runs (14 tasks x OpenCode and Codex), 11:36 to 13:50 pod clock, one
agent at a time: 69.6 tok/s mean output per request, peak KV cache use 8.8%, prefix cache hit rate 94.0%, no
timeouts. One run (T9, OpenCode) ended because a single response reached OpenCode's output limit (16,384
tokens, `opencode/opencode.json`) while still thinking; no other run of any model has hit it.
